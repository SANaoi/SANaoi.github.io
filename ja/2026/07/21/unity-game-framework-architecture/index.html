はじめに

UnityGameFramework は、オープンソースの Unity 向けゲームフレームワークです。ゲーム開発でよく使われる基礎モジュールをまとめて提供しており、開発フローをある程度標準化し、基礎機能の構築を速め、コードの安定性や保守性を高めることができます。

このフレームワークはかなり完成度が高く、実際に商用ゲームで採用された例もあり、コミュニティによる解説やチュートリアルも多く存在します。そのため、プロジェクト開発の基盤としてだけでなく、ゲームフレームワークの設計思想を学ぶ対象としても非常に参考になります。

この記事では、筆者が現在開発している個人プロジェクト RE_BA を切り口に、UnityGameFramework のモジュール構成、実行フロー、そしてその背後にあるフレームワーク設計の考え方を整理していきます。

UnityGameFramework コードリポジトリ：https://github.com/EllanJiang/GameFramework

ゲームフレームワークとは

ゲーム開発では、機能が増えるほどコードの複雑度も急速に上がります。キャラクター制御、シーン遷移、リソース読み込み、UI 管理、イベント通信、データテーブル、本地化、サウンド再生などのシステムを明確な方針なしに作っていくと、後の機能追加や保守が難しくなります。

ゲームフレームワークは、こうした問題を解決するために存在します。単にコードをいくつかの Manager に分けるものではなく、ゲーム開発で繰り返し現れる処理の流れを標準化し、安定した、分かりやすく、再利用しやすい基盤を作るものです。

これは家を建てることに少し似ています。内装や家具の配置を始める前に、設計図を作り、基礎を打ち、構造を組み、水道や電気を通し、窓やドアを取り付け、品質を確認する必要があります。基礎となる工程が安定していれば、後から増築したり修理したりするときにも大きく崩れにくくなります。

ゲームプロジェクトも同じです。成熟したゲームフレームワークでは、次のような内容をあらかじめ決めておくことが多いです。

これらはキャラクタースキル、戦闘演出、UI アニメーションほど目立つものではありません。しかし、プロジェクトが安定して前に進めるかどうかを決める重要な部分です。この記事では UnityGameFramework 風のプロジェクトを例に、ゲームフレームワークが Unity プロジェクトでどのような役割を担い、ばらばらになりがちな MonoBehaviour のロジックをどのように保守しやすい構造へ整理するのかを見ていきます。

一、ゲームフレームワークが解決する主な問題

フレームワークの制約がないプロジェクトでは、最初のうちは多くの機能を素早く実装できます。キャラクターを生成したければ Instantiate を呼び、シーンを切り替えたければ SceneManager.LoadScene を使い、UI を開きたければスクリプトに UI 参照を持たせ、他のモジュールへ通知したければ対象オブジェクトを直接呼び出せます。

この書き方は初期段階では分かりやすいですが、機能が増えるにつれて問題が出てきます。起動順序が制御しにくい、モジュール間の参照が複雑になる、リソース読み込み方式が統一されない、オブジェクトのライフサイクルが分散する、UI 状態とゲーム状態が互いに影響し合う、といった問題です。

ゲームフレームワークが解決しようとしているのは、こうした共通問題です。具体的なゲームプレイロジックを置き換えるのではなく、ゲームをどう起動するか、リソースをどう読み込むか、シーンをどう切り替えるか、オブジェクトをどう生成・破棄するか、UI をどう開閉するか、モジュール間でどう通信するかをあらかじめ定めます。つまり、フレームワークは安定した実行秩序を提供し、その上に各種機能を拡張できるようにするものです。

二、UnityGameFramework の基本的な分層

UnityGameFramework は Game Framework をベースにした Unity 実装です。設計思想としては、ひとつのクラスにすべてを抱え込ませるのではなく、ゲーム実行時によく使う基礎能力を複数のコンポーネントへ分けています。

各コンポーネントは、それぞれ異なる基礎機能を担当します。

業務コードから見ると、GameEntry は統一されたサービス入口のような存在です。UI を開く、リソースを読み込む、エンティティを表示する、イベントを送るといったフレームワーク機能へ素早くアクセスできます。

この設計の利点は、呼び出しが簡単で、ルールが統一され、学習しやすいことです。一方で、モジュール境界を理解せずに GameEntry を万能入口として使いすぎると、業務コードがグローバルサービスへ過度に依存してしまいます。フレームワークは秩序を提供しますが、その秩序を正しく使えるかどうかは、プロジェクト側の規律にも依存します。

もちろん、Procedure はあくまでフローの骨格です。そのフローを実際に動かしているのは、各段階で協調する他のモジュールです。

Resource はリソース読み込みを統一し、業務層がリソースの取得元をできるだけ意識しなくて済むようにします。リソースがエディタ上のディレクトリにあるのか、AssetBundle にあるのか、将来的な更新パッケージにあるのかを、業務層が直接扱わないようにするためです。Entity はゲームオブジェクトのライフサイクルを統一管理します。プレイヤー、敵、弾、アイテム、エフェクト、カメラなどがその対象になります。UI は画面の読み込み、グループ分け、開閉を担当し、入力ロックやマウス表示といったゲーム状態にも影響します。

Event はモジュール間通信を担当し、システム同士の直接参照を減らします。たとえばアイテムを拾うとき、アイテム側のロジックが直接バッグ画面を変更する必要はありません。拾得イベントを送信し、バッグデータと UI 表示がそれぞれ反応すればよいのです。DataTable はキャラクター属性、エンティティのリソース名、UI 設定、弾データ、アイテム説明などをコードから切り離し、設定として扱いやすくします。

四、RE_BA プロジェクトを例にしたフレームワーク協調

UnityGameFramework 風のプロジェクトでは、実際の実行フローはおおよそ次のように理解できます。

大まかな流れは次のようになります。

  1. Init.unity からプロジェクトを起動する。
  2. GameEntry.Start でフレームワークコンポーネントを初期化する。
  3. ProcedureLaunch に入り、言語やリソースバリアントなどの基礎設定を処理する。
  4. ProcedureSplash と ProcedurePreload で、データテーブル、辞書、フォントなどの基礎リソースを読み込む。
  5. ProcedureChangeScene を通して Menu.unity または Game.unity へ切り替える。
  6. ProcedureLevel に入ると、LevelControl がプレイヤー、カメラ、アイテムを表示する。
  7. プレイヤー入力、FSM、拾得イベント、バッグデータ、BagForm がゲームフロー内で協調して動く。

ここから分かるのは、フレームワークが業務ロジックそのものを置き換えているわけではない、ということです。

プレイヤーがどう移動するか、弾がどう命中するか、バッグをどう表示するかは、依然として業務コードが解決する問題です。しかし、プレイヤーをどう生成するか、リソースをどう読み込むか、UI をどう開くか、モジュール同士がどう通信するか、シーンをどう切り替えるかといった共通問題には、フレームワークが統一された経路を提供します。

これこそがゲームフレームワークの中心的な意味です。フレームワークは特定の遊びを面白くしてくれるものではありません。しかし、その遊びを安定して追加し、組み合わせ、保守できるようにしてくれます。

五、フレームワークの利点と代償

ゲームフレームワークを使う利点は分かりやすいです。

一方で、フレームワークには代償もあります。

そのため、フレームワークは複雑であればよいというものではありません。良いフレームワークはプロジェクト規模に合わせて機能するべきであり、プロジェクトがフレームワークに振り回されるべきではありません。

小さなプロトタイプであれば、直接 MonoBehaviour を書いた方が速い場合もあります。一方で、長期保守、多人数開発、大量のリソース、多数のシステムを扱うプロジェクトでは、フレームワークの価値が少しずつ見えてきます。

まとめ

ゲームフレームワークは Manager の寄せ集めではありません。また、すべてのコードを見栄えのよい構造で包むためのものでもありません。本当に解決しているのは、プロジェクトの複雑度が増した後に発生する「整理の問題」です。

フレームワークの価値は、コードを複雑に見せることではありません。プロジェクトが本当に複雑になったときに、機能をどこへ置くべきか、データはどこから来るべきか、オブジェクトは誰が作るべきか、モジュール同士はどう通信すべきかを判断できるようにすることです。

それこそが、ゲームフレームワークのもっとも重要な意味だと思います。
