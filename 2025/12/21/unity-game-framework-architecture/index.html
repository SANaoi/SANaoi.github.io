前言

UnityGameFramework 是一款开源的 Unity 游戏框架，主要对游戏开发过程中常用的基础模块进行了封装。它在很大程度上规范了开发流程，能够加快项目基础功能的搭建，并提升代码的稳定性和可维护性。

这个框架本身已经足够完善：既有基于它开发的商业游戏，也有许多社区开发者围绕它整理教程和实践经验。因此，它不仅可以作为项目开发中的基础框架，也很适合作为学习游戏框架设计的参考对象。

本文会以笔者目前正在开发的个人项目 RE_BA 为切入点，尝试梳理它的模块构成、运行流程，以及背后的框架搭建思路。

UnityGameFramework代码仓库https://github.com/EllanJiang/GameFramework

什么是游戏框架

在游戏程序开发过程中，随着游戏功能不断丰富，代码复杂度也会快速增加。角色控制、场景切换、资源加载、UI 管理、事件通信、数据表读取、本地化、声音播放等系统，如果一开始没有清晰的组织方式，后续功能开发和项目维护就会变得越来越困难。

游戏框架正是为了解决这类问题而出现的。它并不是简单地把代码拆成几个 Manager，也不是为了追求某种看起来更高级的架构，而是把游戏开发中反复出现的流程规范化，形成一套稳定、清晰、可复用的基础设施。

这有点像造房子。真正开始装修和摆家具之前，我们需要先完成设计图纸、打地基、搭建主体结构、水电布线、门窗安装、质量验收等流程。只有这些基础环节可靠，后续扩建、维修和改造才不会牵一发而动全身。

一、游戏框架解决的核心问题

在没有框架约束的项目中，很多功能一开始看起来都能快速完成。需要生成角色，就直接 Instantiate；需要切换场景，就直接调用 SceneManager.LoadScene；需要打开界面，就在脚本中拖一个 UI 引用；需要通知其他模块，就直接拿到对象调用方法。

这种写法在项目初期非常直观，但随着功能增加，问题也会逐渐暴露出来：启动顺序难以控制，模块之间引用混乱，资源加载方式不统一，对象生命周期分散，UI 状态和游戏状态互相影响。

游戏框架要解决的就是这些通用问题。它不是替代具体玩法逻辑，而是提前规定好游戏如何启动、资源如何加载、场景如何切换、对象如何创建和销毁、UI 如何打开和关闭、模块之间如何通信。换句话说，框架提供的是一套稳定的运行秩序，让业务功能可以在这套秩序上继续扩展。

二、UnityGameFramework 的基本分层

UnityGameFramework 是基于 Game Framework 的 Unity 实现。它的设计思路不是让某一个类包揽所有逻辑，而是把游戏运行时常见的基础能力拆成多个组件。

这种设计的优点是调用简单、规则统一、上手速度快。缺点也很明显：如果项目成员不理解模块边界，就容易把 GameEntry 当成万能入口，导致业务代码到处依赖全局服务。框架提供的是秩序，但秩序能不能被正确使用，仍然取决于项目自身的约束。

当然，Procedure 只是流程骨架。真正让流程运转起来的，是其他模块在不同阶段中的协作。

Resource 负责统一资源加载，让业务层尽量不直接关心资源来自编辑器目录、AssetBundle，还是后续的热更新包。Entity 负责统一管理游戏对象的生命周期，例如玩家、敌人、子弹、道具、特效和相机等。UI 负责界面加载、分组、打开与关闭，同时也会影响输入锁定、鼠标显示等游戏状态。

Event 负责模块之间的通信，用事件来减少系统之间的直接引用。例如拾取物品时，物品逻辑不需要直接修改背包界面，而是发送拾取事件，由背包数据和 UI 显示分别响应。DataTable 则负责把角色属性、实体资源名、UI 配置、子弹数据、物品描述等内容从代码中抽离出来，使配置更容易维护。

四、以 RE_BA 项目为例看一次框架协作

在一个 UnityGameFramework 风格的项目中，实际运行流程大致可以这样理解：

大致流程如下：

  1. Init.unity 启动项目。
  2. GameEntry.Start 初始化框架组件。
  3. 进入 ProcedureLaunch，处理语言、资源变体等基础设置。
  4. 进入 ProcedureSplash 和 ProcedurePreload，加载数据表、字典、字体等基础资源。
  5. 通过 ProcedureChangeScene 切换到 Menu.unity 或 Game.unity。
  6. 进入 ProcedureLevel 后，由 LevelControl 显示玩家、相机和道具。
  7. 玩家输入、FSM、拾取事件、背包数据和 BagForm 在游戏流程中继续协作。

这里可以看到，框架并不是替代业务逻辑，而是在业务逻辑之外提供了一套运行骨架。

玩家如何移动、子弹如何命中、背包如何展示，这些仍然是业务代码要解决的问题。但玩家如何被创建、资源如何加载、UI 如何打开、模块如何通信、场景如何切换，这些通用问题都由框架提供了统一路径。

这也是游戏框架最核心的意义：它不负责让某个玩法变得有趣，但它负责让玩法可以被稳定地添加、组合和维护。

所以，框架不是越复杂越好。好的框架应该服务于项目规模，而不是让项目迁就框架。

对于小型原型，直接写 MonoBehaviour 可能更快；对于需要长期维护、多人协作、资源量较大、系统较多的项目，框架的价值才会逐渐显现出来。

总结

游戏框架不是 Manager 大全，也不是把所有代码包一层名字好看的架构。它真正解决的是项目复杂度增长之后的组织问题。

框架的价值不在于让代码看起来更复杂，而在于当项目真的变复杂时，仍然能让开发者知道：功能应该放在哪里，数据应该从哪里来，对象应该由谁创建，模块之间应该如何通信。

这才是游戏框架最重要的意义。
